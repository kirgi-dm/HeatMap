# HeatMap

Учебное приложение FastAPI для управления пользователями и заказами.
Практические работы №7–8: структура приложения и подключение SQLite через SQLModel.
Предметная область адаптирована под текущий вариант проекта: пользователи и заказы.

## Запуск

Из каталога проекта:

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

Главная: http://127.0.0.1:8000/ · Пользователи: http://127.0.0.1:8000/users
· Заказы: http://127.0.0.1:8000/order · Swagger: http://127.0.0.1:8000/docs

Можно также использовать `python -m uvicorn main:app --reload`.

## SQLite: подключение и проверка

Отдельный сервер SQLite не нужен: база представляет собой файл `heatmap.db`
в каталоге проекта. Она создаётся при первом запуске приложения. Путь привязан
к каталогу проекта, а не к текущему каталогу терминала.

1. Установить зависимости и запустить приложение командами из раздела «Запуск».
2. Открыть `/users`, добавить пользователя и посмотреть его ID.
3. Открыть `/order`, создать заказ для этого пользователя.
4. Остановить сервер сочетанием Ctrl+C и снова выполнить `python main.py`.
5. Проверить, что пользователь и заказ остались на страницах.

В `database/connection.py` создаётся `engine` со строкой подключения SQLite.
При запуске `main.py` вызывает `SQLModel.metadata.create_all(engine)`:
создаются отсутствующие таблицы. `get_session()` открывает сессию на запрос
и закрывает её после ответа. `Database` выполняет запросы через эту сессию,
а маршруты получают его через `Depends(get_database)`.

`UserTable` и `OrderTable` описывают таблицы SQLModel; `UserCreate` и
`OrderCreate` проверяют данные форм и JSON. `User` и `Order` описывают ответы.
Поэтому HTML-формы и существующие адреса продолжают работать.

Для отдельной учебной или тестовой базы можно указать другой существующий каталог:

```bash
HEATMAP_DB_PATH=/tmp/heatmap-demo.db python main.py
```

`create_all()` создаёт отсутствующие таблицы, но не изменяет структуру уже
созданных. Для будущих изменений структуры с сохранением данных нужны миграции.

## Структура

```text
HeatMap/
├── main.py                 # создание FastAPI и подключение маршрутизаторов
├── dependencies.py         # общий экземпляр Jinja2Templates
├── models/
│   ├── __init__.py
│   ├── users.py            # схемы UserCreate/User и таблица UserTable
│   └── orders.py           # схемы OrderCreate/Order и таблица OrderTable
├── routes/
│   ├── __init__.py
│   ├── pages.py            # главная страница
│   ├── users.py            # маршруты пользователей
│   └── orders.py           # маршруты заказов
├── database/
│   ├── __init__.py
│   └── connection.py       # подключение SQLite, сессии и операции с БД
├── templates/              # формы, списки, карточки и ошибки
├── heatmap.db              # SQLite, создаётся автоматически и исключена из Git
├── tests/test_app.py       # проверки маршрутов и целостности связей
├── schemas.py              # импорты моделей для совместимости
└── requirements.txt
```

## Данные и идентификаторы

- `User`: `id`, `username`, `email`.
- `Order`: `id`, `name`, `user_id` (ссылка на существующего пользователя).
- `UserCreate` и `OrderCreate` описывают входные данные без `id`.
- ID назначаются сервером автоматически, отдельно для пользователей и заказов.
  У пользователя №1 и заказа №1 могут совпадать номера: это разные сущности.
- ID не меняется при редактировании и не используется повторно после удаления
  в пределах существующего файла БД, в том числе после перезапуска.
- Совпадающие имена пользователей и названия заказов разрешены: записи различаются по ID.
- При изменении имени или email пользователя в карточке заказа сразу отображаются актуальные данные.
- Создать заказ с несуществующим `user_id` нельзя (404).
- Удалить пользователя с заказами нельзя (409). Сначала удалите заказы
  или переназначьте их другому пользователю через редактирование заказа.
- Данные хранятся в `heatmap.db` и сохраняются при перезапуске сервера и reload.
- Связь `orders.user_id → users.id` защищена внешним ключом SQLite.
  Для каждого подключения включается `PRAGMA foreign_keys=ON`.

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | Главная |
| GET | `/users` | Список пользователей и форма добавления |
| POST | `/user` | Создание пользователя из формы |
| GET | `/user/{user_id}` | Карточка пользователя; `?edit=true` открывает редактирование |
| PUT | `/user/{user_id}` | Обновление пользователя, JSON |
| DELETE | `/user/{user_id}` | Удаление пользователя, ответ JSON |
| POST | `/user/{user_id}/edit` | Сохранение формы пользователя |
| POST | `/user/{user_id}/delete` | Удаление пользователя из браузера |
| GET | `/order` | Список заказов и форма добавления |
| POST | `/order` | Создание заказа из формы |
| GET | `/order/{order_id}` | Карточка заказа; `?edit=true` открывает редактирование |
| PUT | `/order/{order_id}` | Обновление заказа, JSON |
| DELETE | `/order/{order_id}` | Удаление заказа, ответ JSON |
| POST | `/order/{order_id}/edit` | Сохранение формы заказа |
| POST | `/order/{order_id}/delete` | Удаление заказа из браузера |

POST-операции с формами после успешного выполнения перенаправляют на список (303).
PUT и DELETE возвращают запись с её ID. Невалидные данные возвращают 422;
отсутствующая запись — 404. GET-страницы возвращают HTML.
Поиск, изменение и удаление по имени заменены операциями по ID.

## Проверка

```bash
python -m unittest discover -s tests -v
```

Проверяются формы и API, автоматическая выдача ID, одинаковые имена,
сохранение связей при переименовании, переназначение заказов,
защита от удаления пользователя с заказами и обработка ошибок.
Дополнительно проверяются внешние ключи непосредственно в SQLite и чтение
сохранённых данных новым процессом приложения. Тесты используют временную БД
и не меняют рабочую `heatmap.db`.

## Соответствие заданию

1. Модели, маршруты и хранилище выделены в отдельные пакеты; маршруты подключаются через APIRouter.
2. Реализованы модели и операции создания, просмотра, изменения и удаления для текущего варианта проекта.
3. Через SQLModel созданы таблицы `users` и `orders`, настроены сессии на каждый запрос.
4. Реализованы постоянное хранение, автоматические ID и защита связи пользователя с заказами.

В методичке пример посвящён планировщику событий и содержит регистрацию и вход.
В HeatMap сохранён текущий вариант с пользователями и заказами; управление
пользователями здесь не является регистрацией или аутентификацией.
Если преподаватель требует именно планировщик событий, необходим отдельный этап
адаптации предметной области и добавления регистрации и входа.
