# HeatMap

Учебное приложение FastAPI для управления пользователями и заказами.
Практическая работа №7: разделение приложения на модели, маршруты и хранилище.
Предметная область адаптирована под текущий вариант проекта: пользователи и заказы.

## Запуск

Из каталога проекта:

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

Главная: http://127.0.0.1:8000/ · Пользователи: http://127.0.0.1:8000/users
· Заказы: http://127.0.0.1:8000/order · Swagger: http://127.0.0.1:8000/docs

Можно также использовать `python -m uvicorn main:app --reload`.

## Данные и идентификаторы

- `User`: `id`, `username`, `email`.
- `Order`: `id`, `name`, `user_id` (ссылка на существующего пользователя).
- `UserCreate` и `OrderCreate` описывают входные данные без `id`.
- ID назначаются сервером автоматически, отдельно для пользователей и заказов.
  У пользователя №1 и заказа №1 могут совпадать номера: это разные сущности.
- ID не меняется при редактировании и не используется повторно после удаления
  в пределах одного запуска приложения.
- Совпадающие имена пользователей и названия заказов разрешены: записи различаются по ID.
- При изменении имени или email пользователя в карточке заказа сразу отображаются актуальные данные.
- Создать заказ с несуществующим `user_id` нельзя (404).
- Удалить пользователя с заказами нельзя (409). Сначала удалите заказы
  или переназначьте их другому пользователю через редактирование заказа.
- Данные хранятся в памяти: при перезапуске, включая автоматический reload,
  пользователи, заказы и счётчики ID сбрасываются. Для работы запускайте один процесс.
  Подключение постоянной БД относится к следующему этапу работы.

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | Главная |
| GET | `/users` | Список пользователей и форма добавления |
| POST | `/user` | Создание пользователя из формы |
| GET | `/user/{user_id}` | Карточка пользователя; `?edit=true` открывает редактирование |
| PUT | `/user/{user_id}` | Обновление пользователя, JSON |
| DELETE | `/user/{user_id}` | Удаление пользователя, ответ JSON |
| POST | `/user/{user_id}/edit` | Сохранение формы пользователя |
| POST | `/user/{user_id}/delete` | Удаление пользователя из браузера |
| GET | `/order` | Список заказов и форма добавления |
| POST | `/order` | Создание заказа из формы |
| GET | `/order/{order_id}` | Карточка заказа; `?edit=true` открывает редактирование |
| PUT | `/order/{order_id}` | Обновление заказа, JSON |
| DELETE | `/order/{order_id}` | Удаление заказа, ответ JSON |
| POST | `/order/{order_id}/edit` | Сохранение формы заказа |
| POST | `/order/{order_id}/delete` | Удаление заказа из браузера |

POST-операции с формами после успешного выполнения перенаправляют на список (303).
PUT и DELETE возвращают запись с её ID. Невалидные данные возвращают 422;
отсутствующая запись — 404. GET-страницы возвращают HTML.
Поиск, изменение и удаление по имени заменены операциями по ID.

## Проверка

```bash
python -m unittest discover -s tests -v
```

Проверяются формы и API, автоматическая выдача ID, одинаковые имена,
сохранение связей при переименовании, переназначение заказов,
защита от удаления пользователя с заказами и обработка ошибок.

## Соответствие заданию

1. Модели, маршруты и хранилище выделены в отдельные пакеты; маршруты подключаются через APIRouter.
2. Реализованы модели и операции создания, просмотра, изменения и удаления для текущего варианта проекта.
3. Диаграмма вариантов использования и основные сценарии находятся в `docs/`.

В методичке пример посвящён планировщику событий и содержит регистрацию и вход.
В HeatMap сохранён текущий вариант с пользователями и заказами; управление
пользователями здесь не является регистрацией или аутентификацией.
Если преподаватель требует именно планировщик событий, необходим отдельный этап
адаптации предметной области и добавления регистрации и входа.
